# 02: 电池页空排行收成紧凑引导行——三提案之③整页观感

**Status:** ready-for-agent

**What to build:** 电池页两张「耗电排行」卡(全部应用 / AI 助手,battery-energy/01
落地)在**助手链不可用或尚无读数时,收成一条紧凑引导行**——一行高的卡:状态
文案 + 单个出口按钮(去开启 / 去批准 / 重新登记,按 gate 四态复用既有文案与
动作)。读到数据(rows 非空)自动恢复两张完整排行卡,卡内容零改动。主卡不动
(与其他页同款标准件,拍板过的一致性)。

**背景:** 电池页改进三提案之③(整页丑待指认)。2026-11-23 grilling 定稿:用户
指认 = 空排行双胞胎死卡 + 整页主次(混合);helper 批准链已搁置
([[battery-energy-redesign]] 11-22 晚拍板),两卡可能长期停在引导空态——两张
一模一样的引导空卡让整页读作「一张活卡 + 两张死卡」。

**拍板(grilling 一轮,2026-11-23 用户「同意」):**

1. Q1 最扎眼 = 空排行双胞胎卡 + 整页主次(A/B 混合,按用户同意我的预判修)。
2. Q2 收法 = **A:空态合并一条紧凑引导行**,数据到了自动展开两张完整卡
   (状态切换一次完成,批准前的日子页面最干净;不选 B 永久合一卡——空态期间
   仍是一张大空卡占位)。
3. Q3 主卡不动。
4. 展开触发 = rows 非空(不猜 gate「快有数据了」,数据说了算);
   enabled-but-等读数/拉取失败也走紧凑行(文案与出口按四态区分,现状
   energyGateEmptyMessage 已有四态文案,复用)。

**分层与文件:**

- 决策纯函数化:MetricTabStack `.battery` 分支的「紧凑行 vs 两张卡」判定抽成
  可测的纯函数(gate + rows 非空 → 布局形态),别散在 builder 里。
- View 新小组件 `EnergyGateHintRow`(名字实施时可调):一行高卡壳(cardShell
  两档)+ 电池 accent 图标 + 状态文案 12pt secondary + 尾部 `.link` 出口按钮
  (RankingEmptyMessage.action 同一动作管线);**先补 DESIGN.md(电池页节)
  再写码**,数值全走令牌表,不自创新档。
- MetricTabStack battery 分支:按判定换发 builder.card / 两个 moduleRanking;
  弹窗 360 与主窗口同源自动生效。
- **捎带挂账小修**:build.sh 指纹守卫「签后再比」——helper 显式签名挪到守卫
  比对之前(签后再比 sha256,消除 ad-hoc 构建产物 vs 签名装机差异打穿守卫的
  误报重批提示;battery-energy/01 挂账原文)。脚本改动,装机日志实证指纹
  判定即可,不起自动化。

**测试:** 判定纯函数几例(四态 × rows 空/非空 → 紧凑行 / 两卡);View 不加
快照(目验归用户)。既有 1409 例不回归。

**冗余搜查(立票即分诊):** 授权型空态引导本身已存在(battery-energy/01 的
RankingEmptyMessage action),本票改**形态**(两卡一空态 → 一行),不重复造
出口管线;`.out-of-scope/` 无同域条目;无产品拍板残留(三问已定);分类=UI
改进;ready-for-agent。

**验收:** 起 app → 电池页——现在看到的是主卡 + 一条一行高的引导行(不再是
两张空排行卡);主窗口与弹窗一致。build.sh 装机时不再出现「指纹变了需重批」
的误提示(helper 未变更时)。
